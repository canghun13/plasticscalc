## Technical reproduction and correction

All following failures were reproduced in a fresh actual production Edge session with `1.5` entered in the displayed Cavities field, all other defaults unchanged:

| Target | Invalid count accepted before fix |
| --- | --- |
| Shot Size | 87.45 g/shot, no error |
| Resin Weight | 133.88 g/shot, no error |
| Material Cost | 0.13 per part, no error |
| Parts Per Shift | 1,257.12 good parts/shift, no error |
| OEE Capacity | 1,127.92 good parts, no error |
| Machine Cost Per Part | 0.37 per part, no error |
| Product Energy Intensity | 0.505 kWh/kg injected, no error |

Controls: Parts Per Hour and Projected Area displayed an error and cleared output under the same fractional count. Existing formulas need a discrete count of producing cavities, not a fractional average across different molds. This correction is **not** a requirement that all expected production outputs, mass or time be integer values.

Root cause: three form builders used `step="any"`/`min="0"`; their `novalidate` forms relied on JavaScript guards, which checked finite/non-negative or positive values but did not enforce the integer cavity contract. Updating attributes alone would not fix typed/submitted values. The newer Parts/Projected handlers already enforce safe positive integers, showing the intended existing product contract.

- `assets/js/calculators.js`: shared raw-input validation rejects non-safe/non-positive `cavities`, marks/focuses the field using existing error machinery and clears results. Three affected registry units now say `whole cavities`. The field builder emits step/min one only for `cavities`; other numeric inputs remain continuous. Existing Parts and dedicated Projected semantics retained.
- `assets/js/phase3-calculators.js`: the three cavity-using tools get the same explicit contract, invalid marker/focus and existing result clear/reset behavior. Regrind/Masterbatch/other Phase 3 methods and formulas unchanged.
- `assets/js/energy-calculators.js`: Product Energy Intensity cavity field gets matching step/min and safe-integer validation, marker/focus and existing error/result clear behavior. Other energy inputs/algorithms unchanged.
- No `parseInt`, rounding a fractional cavity, assumed machine maximum or new pressure/safety threshold. No HTML, CSS, generator, meta/title/H1, sitemap or badge changes. Only three runtime JS files, a regression suite and operational documentation.

Primary sources, not competitor code: [Protolabs multi-cavity molding](https://www.protolabs.com/resources/design-tips/design-considerations-for-multi-cavity-molds/) defines cavities producing multiple physical parts per cycle; [MDN Number.isSafeInteger](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/isSafeInteger) documents the exact-integer numeric boundary; [MDN step](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/step) documents number increments. The positive-integer input requirement follows that discrete count and the site's healthy controls; no manufacturer-specific capacity recommendation is inferred.
